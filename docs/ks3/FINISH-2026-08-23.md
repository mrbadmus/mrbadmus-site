### The write-through, and what it does when it fails

## PHASE 2, UNIT A — the `ks3_cards` mirror

The flashcard deck is built from the lessons a class has covered, so it is
assembled at runtime in the browser — and **the browser cannot read Python**.
There was no path at all from `LESSON["vocabulary"]` to a card in front of a
child. This unit builds it, following `ks3_ladder_questions` exactly: authored
in `ks3_data`, exported by `export_ks3_questions.py`, read directly by the
client under `SELECT to authenticated USING (true)`.

**582 rows: 573 definitions across all 107 lessons, 9 equations across 7, and
ZERO key facts.**

### ⚠️ KEY FACT CARDS ARE DELIBERATELY NOT SHIPPED — and that is a content call

The brief says the deck is *"definitions, key facts, equations"*. Two of those
three exist in the data as authored question→answer pairs. The third does not.

`key_facts[].text` and `key_note` are **statements** — a back with no front. The
obvious front, `big_question`, is unusable at card size: median **148**
characters, and **87 of 107** lessons over 120. So shipping key-fact cards would
mean WRITING a science prompt for every lesson.

**That is Mide's gate, not an export's.** The `kind` CHECK accepts `'key_fact'`
and the exporter emits none, so the day those fronts are authored the migration
does not have to move.

### The two card fronts, and why each is worded as it is

**`Define: <term>`, term verbatim.** Design's `Define diffusion.` breaks on the
real corpus twice. 212 of 573 terms are authored with a capital, and it is
per-unit house style rather than a property of the word — B2, C2, C3, C6–C9
capitalise wholesale; B1, B3–B5, B11 do not — so Design's frame prints
`Define Skeleton.` beside `Define cell.` in one deck. And 143 terms are PHRASES
(`concentration difference`, `sacrificial protection`) which read as fragments
after a verb. Down-casing was rejected: `DNA` and `X-ray diffraction` are both
real terms here and both would be damaged, and a heuristic that mangles two in
573 is worse than a frame needing none. A colon makes the term a **label**, so
an authored capital is not an error and a phrase is not a fragment. Nothing is
normalised.

**`Complete the word equation: <left>`, back the right-hand side.** ⚠️ **This one
is a science-accuracy catch.** Design's `Write the word equation for <X>` has no
honest `<X>`: the lesson title fits two of seven, prints `for Acid + metal.` on a
third, and on `c5-03` would say *"for oxidation"* over an equation that is
specifically **rusting**. Giving the left side asks for the products, which is
what all seven lessons teach, and composes no words of its own.

### The `id` is anchored on the FRONT, never on position

`<lesson_slug>#def#<slug(term)>` / `<lesson_slug>#eq#<slug(left)>`. A positional
id orphans nothing but does the worse thing: insert one term at the top of a
lesson and every id below names a DIFFERENT card, sliding per-card state
(seen / got-wrong) onto the wrong questions. Anchored on the front, reordering
moves nothing and rewriting a definition moves nothing — the id changes only
when the question does.

## THE CACHE-BUST UNIT

### ⚠️ The hole was EIGHT assets, not three

`shared/student-live.js:33-42` loads five MORE shared scripts at runtime from a
`DEPS` array, every one unstamped: `config.js`, `class-entry.js`,
`student-guard.js`, **`student-data.js`**, `ks3-lesson-urls.js`. Stamping only
the three `<script>`/`<link>` tags would have left `student-data.js` — which
carries `saveBenchTheme` and `workingAcademicYear()` — on the identical
four-hour skew, reached through a `<script>` element the build never writes.

They cannot be stamped by rewriting `student-live.js` (hand-written source), so
the build publishes `window.__MRB_ASSET_V__` and the runtime reads it.

⚠️ **The map is keyed on the BARE FILENAME on purpose.** Keyed on
`/shared/<name>` it would be rewritten by `generate_site_v5.py`'s own cache-bust
regex — which matches `/shared/student-data.js"` wherever it occurs, INCLUDING
INSIDE A JSON KEY — turning the key into `"/shared/student-data.js?v=…"` which
the lookup then misses. Silent, and it would look exactly like a stamp with no
effect.

### ⚠️ The build was in the WRONG ORDER, and a naive stamp would have made it worse

`build()` wrote the pages FIRST and published `student-runtime.js`,
`student-live.js` and `ks3-lesson-urls.js` LAST. A stamp computed in the pages
loop would have read the PREVIOUS build's copy and pinned the page to bytes this
build was about to overwrite — `?v=<yesterday>` serving today's file: **the skew
made permanent, with a green build.** `ks3-lesson-urls.js` is the sharpest case
because the build generates it; there is no source file to fall back on.

Two guards, neither a convention:

1. **publish first, stamp second** — the shared-asset publication moved ahead of
   the pages loop;
2. **`_verify_stamps()`** re-reads every named file from disk at the end of
   `build()` and refuses to finish if any hash disagrees with the stamp that
   shipped — in `mrbadmus_site/shared/` AND in `shared/` — plus a scan for any
   surviving unstamped `/shared/…` reference.

Three self-proofs, red then green, including a dep edited out of sync →
*"hashes 06f24811 but the pages shipped ?v=4777dc33 — the stamp names content
that is not what will be served."*

⚑ **The unstamped-link scan was written WRONG first, and gave a FALSE RED on
correct output.** `/shared/[\w.-]+(?!\?v=)` is satisfied by backtracking one
character: on a perfectly stamped `…student-ds.css?v=46b41b81` it matched
`…student-ds.cs`, saw `s` ≠ `?v=`, and reported twelve unstamped links on a clean
page. Now the stamp is an optional group and the test is whether it captured.

### The recorded constraint, checked

Memory records *"the cache-bust stamp forbids splitting built output per unit"*.
Read at source, it means a page carrying `?v=<hash>` names an asset version, so
committing the page without the asset ships a stamp naming content that commit
does not contain. **This change extends that coupling to the student pages**: the
four pages, `shared/student-live.js` and its `mrbadmus_site/` twin go in ONE
commit, never split. Not violated — both trees are written by one generator in
one pass.
