### The write-through, and what it does when it fails

## PHASE 2, UNIT A — the `ks3_cards` mirror

The flashcard deck is built from the lessons a class has covered, so it is
assembled at runtime in the browser — and **the browser cannot read Python**.
There was no path at all from `LESSON["vocabulary"]` to a card in front of a
child. This unit builds it, following `ks3_ladder_questions` exactly: authored
in `ks3_data`, exported by `export_ks3_questions.py`, read directly by the
client under `SELECT to authenticated USING (true)`.

**582 rows: 573 definitions across all 107 lessons, 9 equations across 7, and
ZERO key facts.**

### ⚠️ KEY FACT CARDS ARE DELIBERATELY NOT SHIPPED — and that is a content call

The brief says the deck is *"definitions, key facts, equations"*. Two of those
three exist in the data as authored question→answer pairs. The third does not.

`key_facts[].text` and `key_note` are **statements** — a back with no front. The
obvious front, `big_question`, is unusable at card size: median **148**
characters, and **87 of 107** lessons over 120. So shipping key-fact cards would
mean WRITING a science prompt for every lesson.

**That is Mide's gate, not an export's.** The `kind` CHECK accepts `'key_fact'`
and the exporter emits none, so the day those fronts are authored the migration
does not have to move.

### The two card fronts, and why each is worded as it is

**`Define: <term>`, term verbatim.** Design's `Define diffusion.` breaks on the
real corpus twice. 212 of 573 terms are authored with a capital, and it is
per-unit house style rather than a property of the word — B2, C2, C3, C6–C9
capitalise wholesale; B1, B3–B5, B11 do not — so Design's frame prints
`Define Skeleton.` beside `Define cell.` in one deck. And 143 terms are PHRASES
(`concentration difference`, `sacrificial protection`) which read as fragments
after a verb. Down-casing was rejected: `DNA` and `X-ray diffraction` are both
real terms here and both would be damaged, and a heuristic that mangles two in
573 is worse than a frame needing none. A colon makes the term a **label**, so
an authored capital is not an error and a phrase is not a fragment. Nothing is
normalised.

**`Complete the word equation: <left>`, back the right-hand side.** ⚠️ **This one
is a science-accuracy catch.** Design's `Write the word equation for <X>` has no
honest `<X>`: the lesson title fits two of seven, prints `for Acid + metal.` on a
third, and on `c5-03` would say *"for oxidation"* over an equation that is
specifically **rusting**. Giving the left side asks for the products, which is
what all seven lessons teach, and composes no words of its own.

### The `id` is anchored on the FRONT, never on position

`<lesson_slug>#def#<slug(term)>` / `<lesson_slug>#eq#<slug(left)>`. A positional
id orphans nothing but does the worse thing: insert one term at the top of a
lesson and every id below names a DIFFERENT card, sliding per-card state
(seen / got-wrong) onto the wrong questions. Anchored on the front, reordering
moves nothing and rewriting a definition moves nothing — the id changes only
when the question does.

## THE BOOT-HONESTY UNIT — a deadline, a first paint, and an address that stops lying

Three changes, one unit: the page never leaves a student in the dark, and never

### The deadline — 75s cold, 25s warm, on reads AND writes

`api()` did a bare `await fetch(…)` with no `AbortController`. `run()`'s catch

## THE OFFLINE QUEUE PERSISTS — RULED by Mide

> *"The standing ruling already names the browser copy as 'a cache and an
> offline queue': make it one. Queued answers survive reload, drain on
> reconnect, and the held state is honest — nothing shows as held unless it
> genuinely survives a tab close."*

The queue (`shared/student-live.js:751`, not 539 as the brief said) was a plain
in-memory array. An answer given offline was shown to the student as held and
silently discarded on reload or tab close. **The student saw a tick; the mark
did not exist.**

### localStorage, and the reason is the honesty rule rather than convenience

`confirm` must decide **in the same turn the answer is given** whether it may
show that answer as held, and only a synchronous store can be asked. IndexedDB
would force the page to claim "held" and retract it a tick later — the same
defect in a new hat. One entry is a few hundred bytes; a 15-question assignment
is under 10 KB against 5 MB.

**The key, exactly:**

```
mrbadmusai.answerqueue.v1.<supabase auth user id>.<assignment id>
```

`userId` is threaded `run() → buildAssignment(…, ctx.user.id) → makeSink(…)`. A
second child on the same browser profile computes a different key, reads
nothing, and has no code path to the first child's entries. The blob **repeats
both ids inside itself** and `readStored()` discards any blob whose ids
disagree with the key — so even a key collision could not survive being opened.

### Ordering, supersedes and keepalive duplicates — three mechanisms, no timestamps

1. **The queue is a MAP keyed by question index, never a list.** Answering Q3
   again REPLACES Q3's entry, so "must not overwrite C with B" is not a problem
   to solve — B stops existing the moment C is given.
2. **Pruned against the server at construction**, before the first `flush()` and
   before `resume()`. Any entry whose question the server already answers is
   dropped without comparing values. That covers both histories — the keepalive
   duplicate delivered by a request that outlived the tab, and an answer
   superseded on another device. No timestamp needed: an entry is only ever
   written by a page that had just found the server holding nothing.
3. **`flush()` removes an entry only if it is still the one that was sent**, so a
   newer answer arriving mid-flight is not deleted by the older request's success.

An entry is also dropped if its stored `question_ref` or letter no longer matches
the question at that index — a retired question shifts every index after it, and
a confidently WRONG attribution is worse than a lost answer.

`flush()` now also runs **on the way in** when `navigator.onLine !== false`:
`online` fires on a TRANSITION, and a student who closed the tab offline and
reopened at home is never in one.

### The honest held state

`confirm` asks the sink synchronously and gets `{held, kept}`. **`kept` is
verified, not assumed** — the entry is written, read back and matched before the
page is allowed to say the word. When the store refuses (full, disabled, private
mode) nothing is marked held and the header reads:

> `OFFLINE · 01 NOT HELD ON THIS DEVICE`

§8.10: it says something true about the student's WORK — their answer, counted —
and nothing about storage, quotas or private browsing. It is Design's own
sentence negated, so it cannot be confused with the held state.

⚑ **`drain()` had to be ruled too.** Design's version deleted one held key per
130ms tick *whatever happened on the wire*, headed `BACK ONLINE · 03 SENT` —
honest on Design's page, where nothing is being sent and it is a drawing of
sending; a **false confirmation** on a real one. With a sink, `held` is now a
projection of `sink.pending()`: a hatch clears when the answer has actually
gone. Without a sink the fixture keeps Design's animation byte-identical.

### ⚠️⚠️ A METHODOLOGY FINDING THAT INVALIDATES A CLASS OF TEST

**Neither `Network.emulateNetworkConditions {offline:true}` nor
`Fetch.failRequest` stops a `keepalive: true` fetch.** Measured twice: the
answer reached the database with `navigator.onLine === false` AND the backend
URL pattern armed to fail. Chrome runs keepalive requests out of the browser
process, past both interceptors.

**The first two "offline" drives were therefore not offline on the wire.** Any
future drive of an offline path in this repo that relies on DevTools network
emulation is testing nothing. The offline simulation was rebuilt by pointing
`window.MrBadmusConfig.BACKEND_URL` at a dead address after mount (`post()`
re-reads config on every call).

It also turned the false run into a free and faithful drive of the
keepalive-duplicate case: the row landed, the queue never heard, and on reopen
the prune dropped the entry rather than writing it twice.

Also: **`Page.navigate` deadlocks against Fetch interception of the document** —
the reply does not arrive until the navigation commits, and the pump that would
release it is downstream of the reply.

### Wrong-answer targeting, written ONCE

`rankForPractice(items, opts)` in `shared/student-live.js` — **the one place**,
and Phase 3's recall round calls the same function. The rule is Design's:

```
mine  (a lesson the student got something wrong in)  →  seen (least first)  →  jitter
```

* **wrong answers** come from `assignment_question_attempts` under
  `attempts_self_all`, joined through the student's own submissions;
* ⚠️ **a card id is not a question ref** — questions are `<slug>#recall`/`#apply`,
  cards are `<slug>#def#<term>` — so the join is at **LESSON level**: a lesson
  you got something wrong in makes that lesson's cards `mine: true` and lights
  Design's `FROM YOUR WORK` chip;
* **seen counts** live in `mrbadmusai.cardseen.v1.<auth user id>.<class id>`,
  the same scoping discipline the answer queue established — a second child on
  the same browser profile computes a different key and has no path to the
  first's;
* **jitter is a hash of a fixed seed**, not `Math.random()`, so the deck cannot

### ⚠️⚠️ THE SIXTH MECHANISM, AND IT WAS FOUND BY DRIVING — `SET_EXPR`

Design's overlay draws its pips from `<for e="pips">` (donor 330). **The live

recall round's key, so the later key won. **The flashcards overlay rendered TWO
pips for an eleven-card deck** — the recall round's two questions — each with no
`data-on` at all, because a recall pip's shape is not a card pip's.

> **The build was green. All three gates were green. None of them can open the
> overlay.** Measured in the drive: `n: 2, w: 174, on: ''`.

⚠️ **And ordering is not the fix, because the two surfaces are not mutually
exclusive.** The round is `if onRecall` inside the page; the overlay is grafted
at the design root, outside both views, and `goRecall` does not clear `cards`. A
student who opens the cards and then the round has both, so whichever list won
would be wrong for one of them.

a BINDING NAME, not a drawing — nothing Design drew changes — and the expected
old value is asserted at build time, so a drifting index stops the build instead
of silently repointing some other loop at a list that is not its own.

**This is the second defect this run that lives entirely in the space no gate
watches** (the first being `.rprog`'s hardcoded six steps). Both were found by
looking at the page.
