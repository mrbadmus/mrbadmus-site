## ⚠️ THE FALSE PREMISE — Phase 1 is built on a claim that is not true

The brief opens Phase 1 with:

> Your own finding: harbour-as-default turns `student_parity` red the moment it
> lands.

**It does not, and it cannot, because `student_parity.py` never looks at the
merged page.** That finding came from the previous run's anchor map, which
reasoned about the gate rather than reading it. Read, it says something else
entirely — and something more serious.

### What `student_parity` actually drives

Every one of its eight layers reads the PREVIEW pipeline. Measured, not inferred:

| what | value | so |
|---|---|---|
| `PAIRS` | `student/class-preview.html`, `student/assignment-preview.html` | the pages it drives |
| `COUNT_SOURCES` (layers E, F) | `build_student.py`, `shared/student.js`, `shared/student-assignment.js` | the sources it scans |
| `ks3_parity.ST_SWEEP_PAGES` (layer D) | `student/class-preview.html`, `student/assignment-preview.html` | the pages it sweeps |

There is no path in the file to `student/class.html`, to
`student/class-fixture.html`, to `build_student_port.py`, to
`student_rulings.py`, or to `shared/student-live.js`.

And `build_student.py` — which writes the previews — **applies no rulings at
all**. It loads Design's own standalone in headless Chrome, lets Design's logic
render it, and snapshots the DOM. Confirmed three ways:

* `grep rulings build_student.py` → nothing;
* `class-preview.html` still contains `Settings` twice, so the P7 ruling that
  removed it is not in the preview;
* `class-preview.html` carries 429 `data-dc-tpl` attributes; `class.html` and
  `class-fixture.html` carry **zero** — so a gate keyed on `data-dc-tpl`, which
  is how every one of parity's per-node comparisons is keyed, could not address
  the ported page even if it were pointed at it.

`student_parity` is a gate on the reproduction of Design's original file by the
PREVIEW generator. That is a real and useful thing to gate. It is not a gate on
what the students load.

### The consequence, which runs the opposite way to the brief's

The brief expected a gate that would go red and need a declared divergence. The
truth is a gate that will not move at all — so the themes would ship **unwatched**
rather than watched-and-red.

⚠️ **The live student pages have no design-fidelity gate on colour or layout.**
`student_behaviour.py` is the only gate that drives the ported output, and it
compares visible TEXT and the CONTROL list. Both are strong, and neither can see
a colour. Six themes are precisely a colour change.

### Also wrong, and worth correcting where it is written down

`CLAUDE.md` says of the two gates: *"Both drive `*-fixture.html`, never the live
page."* Half of that is true. `student_behaviour` drives `class-fixture.html`;
`student_parity` drives `class-preview.html`, which is a different file from a
different generator with none of the rulings applied. Corrected in this run.

### What Phase 1 becomes

The brief's *property* is right and is kept verbatim — region-scoped comparison,
a second reference, merged regions held to Design's amended delivery and
untouched regions to the original, declared per region, proved both ways. Only
the gate it is built on changes, from the one that is blind to the merge to the
one that is not.

## ⚠️ THE SECOND FINDING — the amended delivery carries DIFFERENT SAMPLE DATA

The anchor map's plan for the gate was "merged regions compare against Design's
delivery". Measured, that comparison cannot be made at the level of rendered
text, because the two deliveries are not showing the same class.

Rendered at 1460 and read region by region:

| region | original delivery | amended delivery |
|---|---|---|
| hero | `WELCOME BACK, AYO · YOUR CLASS 8r/Sc1 BIOLOGY MR BADMUS…` | `WELCOME BACK, AY · YOUR CLASS 8r/Sc1 SCIENCE YOUR TEACHER…` |
| bench | `Cells & microscopy`, `Eight questions`, `DUE THU 18:00` | `Breathing and gas exchange`, `4 questions`, `DUE THU 3 SEP, 18:00` |
| work list | `AUTUMN TERM`, `ALL 6`, `W04` | `SUMMER TERM`, `ALL 2`, `W01` |
| leaderboard | `TOP OF WEEK 04` | `TOP OF WEEK 01`, `Rae A.`, `240` |

**The proof that this is DATA and not DESIGN is the hero.** Design marked it
`data-port-region="hero"` with **no** `data-port-change` — Design's own
statement that the amendment did not touch it. Its rendered text is
nonetheless completely different. So the text difference cannot be read as a
design difference, on that region or on any other, and a gate that compared
rendered text between the two deliveries would report nine changed regions
where Design says four are untouched.

`data-port-change` is therefore the only trustworthy signal about what Design
amended, which is what it was for.

### What the mechanism has to be instead

Not a region text diff. The port's fixture carries Design's ORIGINAL extracted
values — that is the whole reason the fixture exists — so a merged region on the
port will show `Cells & microscopy` where the amended delivery shows
`Breathing and gas exchange`, forever, correctly, on a page with nothing wrong
with it.

What the merge actually adds to the port is Design's new **chrome**: the words
`FLASHCARDS`, `BENCH THEME`, `Practise recall`, the six theme names, the round,
the done bench. Chrome does not vary with data, and it is exactly what has to be
held to Design's amended drawing.

So the mechanism is the mirror of `RULED_DIVERGENCE`, which strips a ruled span
out of DESIGN's text. `AMENDED_ADDITIONS` strips a registered span out of the
PORT's text, and asserts it three ways before doing so:

  · **present in the AMENDED delivery**, inside the declared region — if Design
    redraws and it stops matching, the registration is stale and goes red;
  · **absent from the ORIGINAL delivery** — if it was always there, it is not an
    addition and the registration is claiming credit for Design's old work;
  · **present in the PORT**, inside the same declared region — if the merge did
    not land, or landed in the wrong part of the page, that goes red.

Everything not registered stays under the existing byte-for-byte comparison
against the original delivery. That is the brief's property exactly — a merged
region matching Design passes, an undeclared change to an untouched region still
fails — with the region scoping carried by Design's own markers rather than by
an index that rots.

## PHASE 4 — the `profiles` hole, PROVEN before it was closed

The previous run found the policy and left the severity open: *"Whether that
matters depends on whether anything still trusts `profiles.role`; the newer
policies read `auth_user_has_scope(...)` instead, which suggests `role` may be
vestigial."*

**`role` is not vestigial.** `auth_user_has_scope` — SECURITY DEFINER, and the
function every newer policy reads — ends like this:

```sql
  -- M1 dual-read fallback (removed at the final advisory flip)
  or (p_scope = 'hod'          and exists (select 1 from public.profiles p
                                           where p.id = auth.uid() and p.role = 'hod'))
  or (p_scope = 'school_admin' and exists (select 1 from public.profiles p
                                           where p.id = auth.uid() and p.role = 'admin'));
```

The dual-read fallback was left in for the M1 migration and never taken out. So
`profiles.role` is still a live grant of scope — and `Users can update own
profile` is `USING (auth.uid() = id)` with no `WITH CHECK` and no column scope,
while `authenticated` holds `UPDATE` on **all 30 columns**.

`auth_user_school_id()` likewise reads `profiles.school_id`, which the same
student also owns.

### Demonstrated, on the TEST project `qeppkiswvclkkwbxmlok`, and reverted

Run as a roster-imported student (one with a `school_id`, which is what every
real student has), via `set_config('request.jwt.claims', …)` and
`set role authenticated` — the same privileges the browser holds with the public
anon key:

| | |
|---|---|
| student wrote their own `role = 'admin'` | **succeeded, no error** |
| `auth_user_has_scope('school_admin')` | **false → true** |
| profiles the student could read | **1 → 39** |
| row restored | `role` back to `student`, verified |

One `UPDATE` a student can type into the browser console turns them into a
school administrator and opens every profile in their school. That is personal
data for 39 people on the test set, and the live set is larger.

⚠️ **A partial guard already exists and is why this needs saying carefully.**
The first attempt used a student with no `school_id` and was refused by a
trigger — `P0001 staff profile requires a school_id unless the person holds a
platform operator grant`. That trigger stops the escalation only for a profile
that has no school. Every roster-imported student has one.

### The fix — a column GRANT, not a policy

The instinct is to write the column list into the policy. Postgres will not do
it. A policy's `WITH CHECK` sees only the NEW row, never the OLD one, so it
cannot say *"`role` must not have changed"* without reading the table back — and
a subquery on `profiles` inside a policy on `profiles` recurses. Column
privileges are the mechanism the database already has, they are checked BEFORE
row security, and they are declarative.

`supabase/migrations/20260822000056_profiles_update_column_scope.sql`, with
`supabase/rollbacks/20260822000056_..._rollback.sql` beside it:

```sql
revoke update on public.profiles from authenticated, anon;
grant update (id, updated_at, first_name, last_name, avatar_url, school_name,
              year_group, exam_board, science_pathway, tier, target_grade,
              strengths, weaknesses, personal_note, bench_theme)
  on public.profiles to authenticated;
alter policy "Users can update own profile" on public.profiles
  using (auth.uid() = id) with check (auth.uid() = id);
```

**The fifteen, and how the list was drawn.** Every column a student's browser
actually writes and nothing else. The only client-side write path to this table
is the fallback upsert in `profile-setup.html`; the PRIMARY path is
`PUT /api/profile` on the backend, which holds the **service role** key and is
untouched by any of this. `service_role` keeps its own column grants, and
`BYPASSRLS` does not bypass column privileges, so the backend's writes go on
exactly as before — asserted, not assumed, in proof 4 below.

**Excluded, and why:**

| column(s) | why |
|---|---|
| `role`, `school_id`, `department`, `key_stage` | identity and enrolment — the four `auth_user_*` functions read these to decide scope |
| `username`, `last_username_change_at` | written only by `set_username`, a SECURITY DEFINER function that re-checks moderation, availability and the 30-day lock. Definer's rights, so it does not need the grant and must not have it |
| `total_xp`, `streak_days`, `last_active` | server-owned counters. Nothing client-side writes them, and a student who could would be marking their own homework |
| `created_at`, `deleted_at`, `external_student_id`, `school_code`, `teacher_name`, `recent_results`, `display_name` | nothing client-side writes them. `display_name` is read by `teacher-profile.html` and written by nothing |

`anon` loses `UPDATE` outright. RLS already refused it — `auth.uid()` is null —
but a grant that is only ever saved by a policy is a grant waiting for the
policy to change.

### Proved four ways, on TEST and then again on PRODUCTION

Run through `set_config('request.jwt.claims', …)` with `set role authenticated`
— the privileges the browser actually holds with the public anon key.

| # | what | result on production |
|---|---|---|
| 1 | student sets `bench_theme` | **ALLOWED**, reads back `chalk` |
| 2 | student writes `role='admin'` | **REFUSED** `42501 permission denied for table profiles` |
| 2 | student writes `school_id` / `department` / `key_stage` / `total_xp` / `username` | **REFUSED**, all five |
| 2 | `auth_user_has_scope('school_admin')` after every attempt | **false** |
| 2 | profiles the student can read | **1** — their own, and no more |
| 3 | anonymous writes `bench_theme` | **REFUSED** |
| 4 | `service_role` writes `role` and `total_xp` | **ALLOWED**, correct — the backend is unaffected |

Production `authenticated` now holds `UPDATE` on **15 columns**, down from 30;
`anon` holds it on none. The one row touched had `bench_theme` restored to NULL
and its `role` verified still `student`. The refusals write nothing by
definition, so no other value on production was altered to run this.

### ⚠️ One thing left open, and it is Mide's

The M1 dual-read fallback inside `auth_user_has_scope` is still there, and its
own comment says *"removed at the final advisory flip"*. It is now harmless —
nothing a student can write reaches it — but it means `profiles.role` is still
load-bearing wherever else it is read. **Whether M1 is finished, and the
fallback can come out, is a call about the schools rollout, not about this
port.** Flagged, not touched.

### Migration versions renamed to what the database recorded

`apply_migration` stamps its own `schema_migrations.version`, so the local files
were renamed to match — `20260821231500_profiles_bench_theme.sql` →
`20260822000050_…`, and the column-scope pair to `20260822000056_…`. Without
that rename a later `supabase db push` re-applies both.
