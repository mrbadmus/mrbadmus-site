- `shared/student-live.js` `buildAssignment()`: new `assignmentLessonHref`

- `build_student_port.py`: `BINDINGS["assignment"]` binds the literal "Open

**The fix broke on the first pass, twice, and both breaks were only visible
by driving the page, never by reading the diff or trusting a green build:**

1. The button rendered with data correct in `MRB_DATA` but never appeared in
   the DOM at all. Cause: `student-runtime.js`'s `build()` resolves both a
   WRAP `<if>`'s condition and a SET_ON `on` handler by looking the name up
   in the component's OWN render scope (`lookup(node.e / node.on, scope,
   …)`) — never by calling `MRB_DATA()` directly and never off `this`. Every
   existing WRAP/SET_ON key (`benchOpen`, `goLessons`, `goClass`, …) is
   already a key in its page's render object for exactly this reason, which
   is what made it easy to add a new one without noticing the pattern.
   Fixed by adding `assignmentLessonHref: MRB_DATA('assignmentLessonHref')`
   and `openLesson: this.openLesson` to the assignment component's own
   return object.
2. Fixing that broke `student_behaviour.py` outright — not a text mismatch,
   a crash (`TypeError: Cannot read properties of null`), because the
   FIXTURE build has no live `student-live.js` data source and `MRB_DATA()`
   throws on a missing key by design ("a missing key is a thrown error and a
   blank page, deliberately" — `build_student_port.py`). The fixture was
   never given a value for the new key. Fixed by adding
   `assignmentLessonHref` to the assignment page's `constants` dict in
   `build_student_port.py`, the same mechanism `weekLabel`/`lateText` already
   used for values a ruling introduces that Design's own file never had —
   given a real-shaped lesson URL rather than a placeholder, so the fixture
   keeps exercising a pressable button.

Both fixes verified live afterward: signed in as the throwaway, opened the

## 3. Recall rounds

Checked first, as instructed — was NOT fully live. `RECALL_MAX` was 6
(`student_rulings.py`), changed to 5 to match spec. Wrong-first,
then-least-seen is real and live (`rankForPractice` in
`shared/student-live.js`). "A fresh shuffle per round" is NOT literally
implemented: rounds walk forward through one day-stable ranked bank in
consecutive `size`-item slices (round 2 picks up where round 1 left off,
`recallRound()` in `student_rulings.py`), not a fresh per-round shuffle.

**Deviation, considered rather than silent:** implementing genuine per-round
randomisation would need the wrong/least-seen ranking machinery (currently
private to `student-live.js`'s data-load closure) exposed across the
LOGIC/data boundary — real new plumbing, not a quickfix-sized change — and a
naive random-window implementation risks REGRESSING the stated goal: a
random start could skip straight past unseen "wrong" items in round 1, where
the current sequential walk guarantees every wrong item is surfaced before
the round ever reaches an already-right one. Left as is; changed only the
round size. If literal per-round reshuffling is wanted, it needs its own
ticket, not a hurry-through here.

The progress bar's six CSS buckets needed no product change — already
generalised (`qStep` scales `step/size` onto them) — but `student_themes.py`
had `min(6, pool)` and three literal pool sizes typed into its OWN

## 6. Three small ones

**a) SEP vs SEPT.** The literal complaint didn't reproduce today — no
"SEPT" anywhere in current output — but the underlying risk was real and
confirmed: `en-GB` Intl's own SHORT month name for September is "Sept" (4
letters, the only month that is), verified against Node's actual ICU data,
not assumed. `fmtDay` asked Intl to spell the month and was one September
away from printing it; `fmtSet` and `fmtStamp` each carried their own
hand-rolled 3-letter array so as not to, which is a second and third copy of
the same 12 words that could drift from each other or from `fmtDay`.
Consolidated into one `MONTHS` array in `shared/student-live.js`, used by
all three formatters; Intl is still asked for the LONDON-correct numbers
(day, month index) but never asked to spell anything. Verified
byte-for-byte identical output to the old implementations across six test
dates — including two in September — before touching the live file.

**Bonus fix found along the way, same family:** `fmtStamp` was reading the
DEVICE's clock (`d.getDate()`/`d.getHours()`) rather than London's, unlike
every other date on the page — a phone carried home from a trip abroad
would have stamped a completion on the wrong day. Now reads London through
the same helper the other two formatters use.

**b) Database read timeouts.** Backend fetches already had a deadline
(`withDeadline`, 75s cold / 25s warm). Nine direct `sb.from(...)` calls in
`shared/student-live.js` had none — able to hang a `Promise.all` (and the
whole page load behind it) indefinitely on a stalled connection. Added
`withDbDeadline` (a 25s race, matching the warm backend budget) and wrapped
all nine call sites.

**c) Two tabs, one Complete.** Verified already correct, both ends, live —
not fixed, because nothing needed fixing:

- Frontend: `handIn()`'s own guard (`if (this.state.handedAt ||
  this.state.handing) return;`) stops a second press in the same tab.
- Backend: fired two genuinely concurrent `POST /api/assignment/complete`
  requests for the same submission (Python `threading`, not sequential) —
  both returned byte-identical `completed_at` timestamps and `"already":
  true`, proving the backend itself is idempotent across tabs, not just
  within one.
